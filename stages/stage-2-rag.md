# 阶段二 · RAG 全链路

| | |
|---|---|
| **周次** | 第 3~5 周 |
| **预计工时** | 30 小时 |
| **前置** | 阶段一已过关 |
| **产出** | `projects/project-1-knowledge-qa/` |
| **一句话目标** | 搭出一条能召回、会拒答、带引用的 RAG 链路，并理解每个环节的失败模式 |

> **心智模型**
> ```
> 离线：原始文档 → 解析 → 清洗 → 切块 → 向量化 → 写入向量库(+元数据)
> 在线：用户问题 → 查询改写 → 混合检索 → 重排 → 组装上下文 → 生成 → 带引用返回
> ```
> **90% 的效果问题出在"没召回到正确的片段"，不是"模型不会答"。** 遇到 badcase，先看检索结果，再怀疑模型。

**语料建议**：用你熟悉的内容，比如某个开源项目的 docs、公司 wiki 导出、或者 Spring 官方文档。**必须是你能判断对错的内容**——用陌生领域的语料，你连答案对不对都看不出来，等于没法调试。

## 任务清单

### T2.1 文档解析（4h）
- [ ] 先只做 Markdown / HTML / 纯文本，**跑通全链路再回头攻 PDF**
- [ ] 清洗：去页眉页脚、导航栏、重复的版权声明
- [ ] 保留结构信息（标题层级、所属章节），后面切块和引用都要用
- [ ] （选做）PDF：Apache Tika / PDFBox 起步，表格和分栏是硬骨头

**这是最脏最重要的一步。** 解析烂了，后面全白搭。

### T2.2 切块策略（4h）
- [ ] 实现基线：固定长度 + overlap（10~20%）
- [ ] 实现结构化切块：按 Markdown 标题层级切，不切断代码块和表格
- [ ] 实现 **Parent-Child**：小块做检索（精确），命中后把所属大块/整节喂给模型（完整）
- [ ] （进阶）**Contextual Retrieval**：入库前用小模型给每个 chunk 生成一句"它在全文中的位置和主题"，拼在前面再做 embedding。配合 prompt caching 做，成本可控

**放进 `labs/lab-01-chunking/`，记录三种策略的对比结论。** 这个对比在阶段三会被 eval 量化，现在先建立直觉。

### T2.3 Embedding 与入库（4h）
- [ ] 选型：中文场景优先 bge-m3 / BGE-zh 系列；云服务也可以
- [ ] **入库和查询必须用同一个模型同一个版本**（换模型 = 全量重建索引，写进 README 提醒自己）
- [ ] 注意 embedding 最大输入长度，超了会被**静默截断**
- [ ] pgvector 建表：向量列 + 元数据列（doc_id、chunk_id、标题、章节、更新时间、租户/权限字段）
- [ ] 建索引（HNSW），理解 `m` / `ef_construction` 的含义

### T2.4 增量索引（3h）
- [ ] 每个文档存 content hash，只重建变化的文档
- [ ] 文档删除时级联删掉它的所有 chunk（别留孤儿数据）
- [ ] 重建时保证**检索不中断**（新旧共存或原子切换）

这是纯工程活，也是你的舒适区。但很多 AI demo 恰恰死在"文档一更新就得全量重跑两小时"。

### T2.5 向量检索（2h）
- [ ] 基础相似度检索，返回 top-k + 距离分数
- [ ] **元数据过滤**：租户、部门、时间、文档类型
- [ ] ⚠️ **权限过滤必须在 SQL 层做**（`WHERE tenant_id = ?`），**绝不能靠 prompt 说"不要泄露别人的数据"**。模型不是安全边界

### T2.6 混合检索（4h）
- [ ] 加 BM25 / 全文检索通道（PostgreSQL 全文检索或 Elasticsearch）
- [ ] 用 **RRF（Reciprocal Rank Fusion）** 融合两路结果
- [ ] 做对比测试：造 5 个含专有名词/编号/代码标识的问题（如 `CVE-2024-1234`、`spring.datasource.hikari.maximum-pool-size`），对比纯向量 vs 混合

**纯向量检索在字符串精确匹配上必挂。** 这个实验会让你印象深刻。

### T2.7 重排（3h）
- [ ] 召回放大到 50~100 条，用 cross-encoder 重排模型精排到 5~10 条
- [ ] 模型：bge-reranker-v2-m3（本地）或云端 rerank 服务
- [ ] 测量：加 rerank 前后的命中率变化、增加的延迟和成本

**单点投入产出比最高的一步**，通常带来 10~20 个点的命中率提升。

### T2.8 查询改写（3h）
- [ ] **指代消解**：多轮里"它多少钱？"必须先改写成"iPhone 17 Pro 多少钱？"，否则检索必挂。**这是多轮 RAG 的头号 bug**
- [ ] （进阶）Multi-Query：一个问题拆成多个检索式取并集
- [ ] （进阶）HyDE：先让模型编一个假答案，用假答案去检索
- [ ] 注意：改写多花一次 LLM 调用，要权衡延迟

### T2.9 生成与引用（3h）
- [ ] Prompt 明确三条：只根据提供的资料回答 / 资料里没有就说不知道 / 每句话标注来源编号
- [ ] **引用做成结构化的**（片段 id → 原文位置），不要让模型自由发挥写来源——**引用本身也会幻觉**
- [ ] 上下文顺序：最相关的放最前或最后（中间容易被忽略，即 "lost in the middle"）
- [ ] 前端/接口返回时，引用要能点击跳回原文

## 🎫 过关卡片

### 🎯 硬指标

先准备一份小测试集（这是阶段三黄金集的雏形）：

| # | 指标 | 达标线 | 怎么测 |
|---|---|---|---|
| 1 | 语料规模 | ≥ **500** 个 chunk | 查库 |
| 2 | 冷门事实召回 | 10 题中命中 **≥ 8** | 挑只出现在**单个 chunk** 里的细节出题，检查正确片段是否进了 top-5 |
| 3 | 拒答能力 | 10 题中正确拒答 **≥ 9** | 问知识库里**确实没有**的问题，看是否编造 |
| 4 | 多轮指代 | 5 组追问中命中 **≥ 4** | "X 是什么" → "那它的默认值呢" |
| 5 | 混合检索有效性 | 5 个含编号/专有名词的问题，混合检索命中率 **明显高于**纯向量 | 对比实验，有数据 |
| 6 | 增量索引 | 改一个文档后重建，日志证明**只处理了该文档** | 看日志 |
| 7 | 端到端延迟 | P95 **< 5s**（含改写 + 检索 + rerank + 首字） | 压测 |
| 8 | 权限隔离 | 用 A 租户身份，**无法**检索到 B 租户的任何 chunk | 构造测试 |

### 🖥 演示题

演示 Project 1，完成一次完整问答：
1. 问一个需要跨两个文档才能回答的问题，回答正确且**标注了两处来源**，点击能跳回原文。
2. 追问一个带指代的问题，命中正确。
3. 问一个知识库里没有的问题，系统说"不知道"而不是编造。
4. **打开调试面板**，说明这次召回了哪 5 个片段、rerank 前后排序变化、为什么第一名是它。

第 4 条最关键——能解释检索结果的人才算真的搭出了 RAG。

### 🗣 口试题（合上电脑作答）

1. 为什么必须做混合检索？举一个纯向量检索必然失败的具体例子。
2. Parent-Child 切块解决了什么矛盾？
3. 为什么权限过滤不能在 prompt 层做？如果有人坚持这么做，会发生什么？
4. 一个 badcase 摆在面前，你怎么在 3 分钟内判断是"检索问题"还是"生成问题"？
5. 换一个 embedding 模型，需要做什么？为什么？
6. "lost in the middle" 是什么，它如何影响你组装上下文的顺序？

### ✅ 通过标准

硬指标 **7/8**（第 5 条混合检索有效性和第 3 条拒答能力**必须过**），演示题 4 条全过，口试题答对 **5/6**。

## 常见卡点

| 症状 | 大概率原因 |
|---|---|
| 明明文档里有，就是搜不到 | ① 切块把关键信息切断了 ② 没做混合检索，问题里的专有名词匹配不上 ③ 元数据过滤条件写错，把正确结果过滤掉了 |
| 检索结果全是不相关的 | ① 入库和查询用了不同的 embedding 模型/版本 ② 向量没归一化 ③ 距离度量用错（cosine vs L2） |
| 多轮对话第二个问题就崩 | 没做指代消解，直接拿"它多少钱"去检索 |
| 回答里有文档里没有的内容 | ① prompt 没写死"只根据资料回答" ② 召回的片段和问题无关，模型退而用自己的知识回答（此时要拒答） |
| 引用的来源是错的 | 让模型自由生成引用了。改成结构化引用 |
| 长文档 embedding 效果差 | 超过模型最大输入长度被静默截断了 |
| 加了 rerank 反而变慢很多 | 召回数量放太大（几百条），或 rerank 模型跑在 CPU 上 |
| PDF 解析出来是乱的 | 分栏/表格。先用结构化文档跑通链路，PDF 单独立项攻 |
