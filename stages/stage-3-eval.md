## 任务清单

### #22 · T3.1 构建黄金集（6h）

这是本阶段最花时间、也最有价值的工作。

- [ ] 收集 **50~200 条**，每条包含：`问题` + `标准答案` + `应该命中的 chunk id 列表`
- [ ] 来源优先级：**真实用户问题日志 > 业务同学出题 > LLM 从文档反向生成**
- [ ] 用 LLM 生成的题**必须人工过一遍**，机器出的题往往过于表面（答案直接抄原文一句话），测不出真实能力
- [ ] 刻意设计难题分布：
  - 简单直答（约 30%）
  - 需要跨多个片段综合（约 25%）
  - 含专有名词/编号/代码（约 15%）
  - 多轮指代（约 15%）
  - **知识库里没有、应该拒答的**（约 15%）
- [ ] 存成结构化文件（JSON / YAML），进 Git 版本管理

**最后那 15% 的拒答题最重要**——一个只会答题不会说"不知道"的系统，在生产环境是危险品。

### #23 · T3.2 检索层指标（3h）
- [ ] **Recall@k**：正确片段是否进了 top-k（k = 1/3/5/10 都算一下）
- [ ] **MRR**：第一个正确结果的排名倒数，衡量排序质量
- [ ] （选做）NDCG：考虑多个相关片段的排序质量

**检索指标和生成指标必须分开算。** 混在一起你就永远定位不了问题出在哪一环。

### #24 · T3.3 生成层指标（5h）
- [ ] **忠实度（Faithfulness）**：答案里的每个论断是否都能在给定上下文中找到依据 → **这就是幻觉检测**
- [ ] **答案相关性**：是否答到点上（而不是正确但答非所问）
- [ ] **引用准确率**：标注的来源是否真的支撑了那句话
- [ ] **拒答正确率**：该拒答的拒了吗？不该拒的误拒了吗？

**LLM-as-Judge 的三个坑，必须避开：**
1. **裁判模型要 ≥ 被测模型**。用弱模型评强模型，评出来的是噪声。
2. **评分标准写成明确的 rubric**（打分表：什么情况给 1 分、什么情况给 3 分、什么情况给 5 分），不要问"你觉得好不好"。
3. **控制随机性**，保证同一批题目重复跑结果稳定，否则你分不清是"改进有效"还是"裁判今天心情不同"。

### #25 · T3.4 一键运行（3h）
- [ ] 做成一条命令（JUnit 测试 / Maven 插件 / `go test` / 独立脚本都行）。**只用一种语言实现，不要做两遍**
- [ ] 输出：总分 + 分项指标 + **每道题的明细**（便于看 badcase）
- [ ] 结果存成 CSV/JSON，文件名带时间戳和配置标识，方便横向对比
- [ ] **记录本次运行的完整配置**（模型、chunk 策略、是否 rerank、prompt 版本）——否则一周后你看着一个 0.81 的分数，想不起来它是哪个版本跑的

### #26 · T3.5 三组对照实验（3h）

用 eval 把阶段二凭直觉做的选择全部量化：

- [ ] **实验 A**：chunk 策略 —— 固定 512 vs 固定 1024 vs Parent-Child vs Contextual
- [ ] **实验 B**：检索方式 —— 纯向量 vs 混合检索 vs 混合 + rerank
- [ ] **实验 C**：模型档位 —— 强模型 vs 中档模型（质量差多少、成本差多少、延迟差多少）

每组实验写进 `labs/` 并给出结论。**实验 C 会直接告诉你成本优化的空间在哪。**

## 🎫 过关卡片

### 🎯 硬指标

| # | 指标 | 达标线 |
|---|---|---|
| 1 | 黄金集规模 | **≥ 50** 条，且每条标注了 ground-truth chunk id |
| 2 | 难题覆盖 | 五类题型（直答/综合/专名/指代/拒答）**每类 ≥ 5 条** |
| 3 | 一键运行 | **一条命令**跑完全部题目并输出结构化结果 |
| 4 | 稳定性 | **同一配置连续跑两次，总分波动 < 3%** |
| 5 | 对照实验 | 完成 **3 组**，每组有数据、有结论、有决策 |
| 6 | 优化闭环 | 至少一次**基于 eval 结果的优化**，使 Recall@5 提升 **≥ 5 个百分点** |
| 7 | 归档 | 每次运行结果可追溯到当时的完整配置 |

第 4 条（稳定性）是最容易被忽略的硬指标。**一个每次跑分都漂 10 个点的 eval，比没有 eval 更糟糕**——它会让你基于噪声做决策。

### 🖥 演示题

1. 敲一条命令，当场跑完 eval，展示分数报告。
2. 打开 badcase 列表，随机挑一条，**当场判断它是检索失败还是生成失败**，并说出下一步改什么。
3. 展示实验 B 的对比数据，用一句话说清楚"为什么我们的链路里有 rerank"。

### 🗣 口试题（合上电脑作答）

1. 为什么检索指标和生成指标必须分开算？各举一个只有分开算才能发现的问题。
2. 什么是 LLM-as-Judge？它最容易在哪三个地方失真？
3. 你的黄金集里为什么要放"应该拒答"的题？不放会怎样？
4. 有人说"我们上线后用用户点赞率当指标就够了"。这个说法的问题在哪？
5. Recall@5 = 0.85、忠实度 = 0.92，但用户还是抱怨不好用。你会去查什么？

### ✅ 通过标准

硬指标 **7/7**（本阶段不允许打折，这是后面所有优化的地基），演示题 3 条全过，口试题答对 **4/5**。

## 常见卡点

| 症状 | 大概率原因 |
|---|---|
| 同一配置两次跑分差很多 | ① 裁判模型随机性没控制 ② 题目太少（< 30 条时单题波动会放大） ③ rubric 写得模糊，裁判自由发挥空间大 |
| 分数很高但实际体验很差 | 黄金集太简单。多半是 LLM 生成的题没人工筛，答案直接抄原文 |
| 忠实度分数总是接近满分 | rubric 没写清"什么算不忠实"。要明确：上下文没提到的具体数字、人名、结论，都算幻觉 |
| 改了 prompt 分数反而降了 | 好事，说明 eval 在工作。回滚，然后一次只改一个变量 |
| 建黄金集太费时间想放弃 | 先做 30 条跑起来，边用边补。**30 条能用的 eval 远胜于 200 条永远建不完的** |
| 检索指标高但生成指标低 | 召回对了但模型没用好：检查 prompt、上下文顺序、片段是否被截断 |
| 检索指标低但生成指标看着还行 | 危险信号——模型在用自己的知识编答案，而不是用你的资料 |

## 💡 本阶段的长期价值

做完这一步，你会拥有一个别人很难快速复制的能力：**用数据说话**。

面试时，"我们把 Recall@5 从 0.62 优化到 0.85，单次问答成本从 0.08 降到 0.02" 这一句话，
胜过背出十个框架的名字。**有 eval 数据 > 有成本数据 > 有安全设计 > 用了多少新框架。**
