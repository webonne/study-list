### R01 read-timeout 对流式是总时长上限，不是空闲超时

**级别**：🔴　**位置**：`LlmClientConfig`（`requestFactory.setReadTimeout`），`ChatService.chatStream`

**现象**：一个健康的流，只要总耗时超过 `read-timeout`，就在中途被切断。默认 120s，意味着任何超过 2 分钟的回答都会被截断；截断的半段回答还会作为完整回答写进历史。

**实测**（`--app.llm.read-timeout=5s`，上游正常吐 20 段、共约 6s）：

```
4.84s  data:{"text":"字16 "}          ← 客户端只收到 17 段
mock:  CLIENT_CLOSED after sent=18
app:   chat stream failed sessionId=d1
```

**说明**：评审时一开始怀疑的是反方向的问题（超时管不住流式正文、线程会永久卡死）。实测证明超时**会**生效，把上游卡住的连接在 5s 时断开，线程也回到了空闲状态——问题在于它按**总时长**算。

**修复方向**：
- 流式和非流式的超时分开配：流式的总时长放宽（或不设）。
- 另做**空闲超时**：两段之间超过 N 秒没有新数据就关掉上游（可以用一个定时任务检查"最后一次收到数据的时间"）。
- 超时导致的中断，不要把半段回答当作完整回答写进历史（或标记为未完成）。

**验收**：read-timeout 设为 5s 时，6s 的正常流能完整结束；上游卡住（消息含 `STALL`）时，在空闲超时后断开。

### R02 TTFT 不含排队时间

**级别**：🔴　**位置**：`ChatService.runStream`（`startedAt` 在工作线程里取）

**现象**：计时从工作线程开始执行时算起，线程池排队的时间没算进去。**过关卡片里"TTFT P95 < 2s"会假通过**，而且恰好是在负载最高、最需要这个指标的时候。

**实测**（8 条并发流占满线程池后发第 9 条）：

```
客户端实际等到首字: 6.00s
服务端报告 ttftMs:   12 ms
```

**修复方向**：在 `chatStream()` 入口取时间传给 `runStream`。可以同时记录 `queueMs`（入口到开始执行）和 `ttftMs`（入口到首字），两个都有用。

**验收**：用上面的方法复现，服务端报告的 ttftMs 与客户端观察到的首字时间相差不超过 100ms。

### R03 排队中断开的客户端仍会调用上游

**级别**：🔴　**位置**：`ChatService.chatStream` / `runStream`

**现象**：客户端在排队时就断开了，等到有空闲线程后，仍然发出上游请求，还把收到的第一段写进了历史。

**实测**（线程池占满，第 10 条在 1.5s 时断开）：

```
mock: START msg='排队时就走了' → CLIENT_CLOSED after sent=2
app:  chat stream cancelled sessionId=q10 chars=3     ← "字0 " 被写进了历史
```

**根因**：Tomcat 只有在**写数据**时才能发现客户端已断开。请求排队时一个字节都没写过，`onCompletion` / `onError` 都不会触发，`cancelled` 一直是 false。

**修复方向**：
- `chatStream()` 返回前先发一条 SSE 注释（如 `: queued`），此后定期发心跳。写数据让断开能被及时发现，心跳还能防止中间代理把空闲连接断掉。
- `runStream` 开头、发上游请求之前再检查一次 `cancelled`。

**验收**：排队中断开的请求，mock 日志里**不出现**对应的 `START`，历史里也没有这一轮。

### R04 INFO 级别打印完整请求报文

**级别**：🟡　**位置**：`LlmClientConfig` 的 `requestInterceptor`

**现象**：每次请求都把完整 JSON（含全部历史和用户原话）用 INFO 打进日志。
- 隐私：用户说的话全部落进日志（阶段五 T5.5 会专门讲"日志里的 prompt 也要脱敏"）。
- 日志量：每次都打全部历史，随轮数**平方**增长。

**修复方向**：改成 DEBUG；INFO 只打摘要（模型、消息条数、总字符数）。

**验收**：默认配置下日志里没有 `"content"` 字段。

### R05 流式调用拿不到 usage

**级别**：🟡　**位置**：`ChatCompletionChunk`、`OpenAiSseDecoder`

**现象**：流式路径没有解析 usage，token 用量和缓存命中在流式调用里完全看不到。#05（缓存命中率）和 #07（计量）会有盲区。

**修复方向**：先查 DeepSeek 文档，确认流式时 usage 是否出现在最后一个 chunk、是否需要额外参数（OpenAI 需要 `stream_options: {"include_usage": true}`，DeepSeek 以官方文档为准）。确认后在 `ChatCompletionChunk` 加 `usage` 字段，`done` 事件和日志里带上。

**验收**：一次流式调用结束后，日志里有 prompt / completion / cacheHit / cacheMiss 四个数。

### R06 线程池队列无上限

**级别**：🟡　**位置**：`ChatStreamConfig`（`Executors.newFixedThreadPool(8)`）

**现象**：`newFixedThreadPool` 的队列无上限，加上 `SseEmitter(0L)` 不设超时，突发流量只会默默排队、占内存；客户端只看到连接开着、没有字。（R02、R03 的实测就是在这个排队状态下做的。）

**修复方向**：用 `ThreadPoolExecutor` 显式构造，给队列设上限；满了直接拒绝，返回 503（或 429），让客户端知道该重试。

**验收**：并发数超过"线程数 + 队列上限"时，多出来的请求立刻收到 503。

### R08 同一会话并发请求会把历史写乱

**级别**：🟡（骨架遗留，不是这次引入的）　**位置**：`ChatService` 读历史 → 调用 → 写历史

**现象**：同一个 sessionId 的两个请求同时进来，都读到同一份历史，写回时交错成 `user1, user2, asst1, asst2`。流式调用要几秒才写历史，比非流式更容易撞上。

## 值得记住的两点

- **评审时一开始判断错了**：以为读超时管不住流式正文，线程会挂死。实测后发现它不会挂死，真正的问题在另一头——超时按**整个请求**算，正常的长回答也会被切断。流式需要的是"两段之间"的空闲超时。**读代码得出的判断，要用实测确认。**
- **客户端断开不会被立刻发现。** 服务端只有在往连接里**写数据**时才知道对方走了。没写过数据的请求（排队中、上游卡住时），断开了也没人知道——所以流式接口要有心跳。
